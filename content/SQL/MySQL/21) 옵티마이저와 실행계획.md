# **옵티마이저와 실행계획**

- **옵티마이저(Optimizer)**​는 SQL을 가장 빠르게 실행할 수 있는 방법을 선택하는 MySQL의 핵심 기능이다.
- 사용자가 작성한 SQL을 그대로 실행하는 것이 아니라, 여러 실행 방법 중 가장 효율적인 방법을 선택하여 실행한다.

예를 들어 하나의 SQL도
1. 어떤 테이블부터 조회할지
2. 어떤 인덱스를 사용할지
3. 어떤 순서로 JOIN할지
등을 옵티마이저가 결정한다.

즉, 옵티마이저는 SQL의 가장 효율적인 실행 방법을 결정하는 역할을 한다.

**실행계획(Execution Plan)**​은 옵티마이저가 선택한 SQL의 실행 방법을 보여주는 정보이다.

실행계획을 보면
1. 어떤 테이블부터 조회하는지
2. 인덱스를 사용하는지
3. 테이블 전체를 검색하는지
4. JOIN은 어떤 순서로 수행하는지
5. 정렬이나 임시 테이블이 필요한지

등을 확인할 수 있다.

즉, 실행계획은 옵티마이저가 SQL을 어떻게 실행할 것인지 보여주는 설계도(계획서)이다.

정리하자면, 옵티마이저는 가장 빠른 방법을 선택하여 SQL을 실행하고, 실행계획은 그 방법을 확인하고 성능을 분석하는 데 사용된다.

**2. Workbench에서 실행계획 보기**

**1) SQL 작성**

```sql
SELECT
    c.name AS category, f.title, f.length, a.first_name, a.last_name
FROM category c
JOIN film_category fc
    ON c.category_id = fc.category_id
JOIN film f
    ON fc.film_id = f.film_id
JOIN film_actor fa
    ON f.film_id = fa.film_id
JOIN actor a
    ON fa.actor_id = a.actor_id
WHERE c.name = 'Action' AND f.length >= 120
ORDER BY f.length DESC;
```

조인문의 순서나 WHERE절안의 순서를 바꾸어도 옵티마이저는 위 순서데로 진행한다. 조인에서는 행의 수가 가장 적은 CATEGORY테이블을 가장 먼저 접근하는 것이 가장 효율적이고, WHERE절에서는 더 많이 필터링할 수 있는 ACTION 장르를 필터링하는 것이 더 효출적이기 때문이다.

**옵티마이저는 SQL을 작성한 그대로 실행하는 것이 아니라, 가장 빠른 실행 순서를 결정한 후 실행한다.**

**[실행계획 해석]**
**① 옵티마이저는 c(category)부터 16행 Full Scan으로 읽기로 결정했다.**
- **c(category) ALL :** category 테이블이 16행밖에 없기 때문에 index를 사용하지 않고 Full Scan으로 읽는다.
- **rows 16 :** 16행이면 인덱스를 사용하는 것보다 그냥 다 읽는 게 더 빠르다."라고 옵티마이저는 판단

- **Extra Using filesort :** 정렬 작업을 수행(ORDER BY f.length DESC), 정렬은 마지막에 실행되는 작업이지만, extra(추가작업)에는 나중에 추가되는 작업도 함께 표시된다.

**② fc(film_category)의 FK 인덱스를 이용하여 Action장르를 찾는다.**
- **rows 62 :** Action 장르 영화가 약 62건이라고 예상한다.

**③ f(film)에서 영화 정보를 찾는다.**
- **rows 1 :** PK로 영화 한 건 조회, 영화 하나당 film은 PK라 1개

**④ fa(film_actor)에서 배우들을 찾는다.**
- **rows 5 :** PK로 영화 한 건 조회, 영화 하나당 배우가 평균 5명

**⑤ a(actor)에서 배우 이름을 찾는다.**
- **rows 1 :** 배우 한 명 조회, film_actor에서 actor_id 하나를 가져오면 actor 테이블에서는 PK로 배우 1명을 찾는다.
