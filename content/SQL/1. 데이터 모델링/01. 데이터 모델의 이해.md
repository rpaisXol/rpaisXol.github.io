# 01. 데이터 모델링의 이해

## 1. 모델링

- 모델링(Modeling)이란 현실 세계의 정보를 컴퓨터가 이해하고 처리할 수 있도록 '구조화'하는 과정
- 현실에 존재하는 사람, 물건, 사건 등을 그림과 도표와 같이 체계적인 형태로 표현
- 모델링은 현실을 추상화하여 표현
- 추상화 된 결과물은 반드시 공동체가 합의한 표기법에 따라 작성
- 예) ERD(Entity Relationship Diagram)
- 공통된 표기법은 분석, 설계, 개발 단계에 걸친 관련자들에게 정확한 의사소통 기준 제공
- 결과적으로 협업을 위한 객관적인 설계도로 기능

## 2. 모델링 특징

### 1. 추상화

- 현실의 복잡한 정보 → 모델 목적에 부합하는 핵심 정보만 선별
- 불필요한 세부 사항 제거, 본질에 집중

### 2. 단순화

- 복잡한 관계나 구조 → 누구나 쉽게 이해, 표현 방식 단순화
- 복잡한 관계나 구조 → ERD 등을 통해 시각적 단순화, 모델의 가독성과 이해 높임

### 3. 명확화

- 구축된 데이터 모델 → 해석 모호함 없음
- 모델의 구성 요소는 누가, 언제, 어디서보더라도 동일한 의미로 해석
- 업무 관련자 간의 의사소통 과정에서 발생하는 오해의 소지 차단
- 복잡한 관계나 구조 → ERD 등을 통해 시각적 단순화, 모델의 가독성과 이해 높임

## 4 모델링의 최소화: 중복 최소화, 비유연성 최소화, 비일관성 최소화

$$
\mathbf t_{\parallel}=\frac{\mathbf r^T\mathbf t}{\mathbf r^T\mathbf r}\mathbf r,
\qquad \mathbf t_{\perp}=\mathbf t-\mathbf t_{\parallel}
$$

- 1. 중복(Duplication) 최소화: 같은 데이터를 여러 군데 반복해 저장하지 않음, 데이터 중복 시 저장 공간 낭비, 한 곳만 수정해도 다른 곳이 바뀌지 않으면 오류 발생
- 2. 비유연성(Inflexibility) 최소화: 데이터 구조를 쉽게 확장 혹은 수정 가능, 이를 통해 데이터 구조와 업무 프로세스 변경 시 시스템의 영향 최소화
- 3. 비일관성(Iconsistency) 최소화: 데이터 간의 상호 참조 관계를 정의, 향 후 데이터 모순이나 불일치가 발생하지 않고 일관된 상태 유지

## 3. 모델링 세 가지 관점

- 성공적인 DB 구축을 하기 위해선, 데이터가 어떻게 흐르고, 무엇과 연결, 어떤 과정을 걸처 처리 되는지에 대한 전체적인 시각 필요 
- 모델링은 데이터 관점, 프로세스 관점, 데이터와 프로세스 상관 관점을 바라보는 것이 중요

### 1. 데이터 관점(What: 무엇을 다룰 것인가)

업무를 구성하는 데이터 자체에 집중하는 관점

- 어떤 데이터들이 존재, 이들이 서로 어떤 관계를 맺는지 모델링
- 예) 병원 → 환자, 의사, 진료기록 등의 데이터가 어떤 구조로 연결되는지 생각

### 2. 프로세스 관점(How: 어떻게 처리할 것인가)

업무를 구성하는 데이터가 어떤 기능이나 절차로 처리되는 관점

- 시스템이 수행해야 할 업무와 흐름을 중심으로 모델링
- 예) 병원 → 환자 등록 > 진료 예약 > 진료 > 진료비 정산 등의 업무가 어떤 순서로 흘러가는지 모델링함

### 3. 데이터와 프로세스의 상관 관점(Why: 왜 그렇게 처리하는가)

데이터와 프로세스가 서로 어떻게 영향을 주고받는지에 집중하는 관점

- 특정 데이터가 어떤 프로세스에 의해 생성되고 변경되는지 분석, 둘의 관계 모델링
- 예) 병원 → **진료 예약이란 업무는 왜 필요한가?**, 환자 정보와 의사 일정 데이터를 함께 고려해 예약을 잡아야 하기 때문이다.

## 4. 모델링 세 가지 단계
- 데이터 모델링은 추상적인 업무 이해 수준에서 출발
- 실제 DB 구축에 이르기까지 점진적으로 구체화, 총 3단계로 이루어짐

### 1. 개념적 데이터 모델링(Conceptual Data Modeling)
- 업무 이해를 바탕으로 데이터의 핵심을 만드는 가장 추상적인 단계
- 기술적인 요소는 배제, 데이터 주체(엔터티)와 이들 간의 관계를 정의하는데 집중

### 2. 물리적 데이터 모델링(Logical Data Modeling)
- 개념 모델을 바탕으로 데이터 논리적 구조를 설계
- 이 과정에서 Key, 속성, 관계 등을 구체적으로 표현
- 특정 DB 기술에 종속 안 됨, 재사용성이 높음

### 3. 물리적 데이터 모델링(Physical Data Modeling)
- 논리적 모델을 특징 DBMS에 실제로 구현하기 위해 변환하는 최종 단계
- 데이터 타입, 인덱스, 저장 방식 등 물리적인 요소를 모두 결정

## 5. ANSI-SPARC의 3단계 스키마 구조와 데이터 독립성

데이터 독립성이란, 데이터 저장 구조가 변경되더라도 응용 프로그램은 영향을 받지 않도록 하는 특성, 시스템의 유지 보수 효율을 크게 높임

### 1. 외부 스키마(External Schema)
- **사용자, 응용 프로그램의 관점**에서 필요한 데이터만 선별해 보여주는 개인화 뷰(View)
- 여러 개의 외부 스키마가 존재
- 예) 영업팀 → 고객 정보만 보여줌 / 인사팀 → 직원 정보만 보여줌

### 2. 개념 스키마(Conceptual Schema)
- **설계자 관점** → DB 전체를 정의하는 통합된 뷰(View)
- 모든 외부 스키마 통합, 조직이 관리해야할 모든 데이터와 그 관계를 하나의 구조로 정의

### 3. 내부 스키마(Internal Schema)
- **개발자 관점**에서 데이터가 디스크에 실제로 어떻게 저장될지 정의하는 물리적 뷰(View)
- 데이터 타입, 인덱스, 저장 파일 경로 등 물리적인 모든 세부 사항 포함

![[01. 데이터 모델의 이해-1791110844704.webp]]
DB의 논리적 구조나 물리적 저장 방식이 변경되더라도, 다른 계층에 미치는 영향을 최소화

### 논리적 독립성
- 전체 데이터 구조(개념 스키마)가 변경되더라도, 사용자가 응용 프로그램(외부 스키마)은 영향을 받지 않는 특성
- 예) 관리자 → 전체 DB에 새로운 테이블 추가되도 기존 사용자는 자신의 프로그램 수정 필요 X

### 물리적 독립성
- 데이터 물리적 저장 방식(내부 스키마)이 변경되더라도, 눈리적 구조(개념 스키마나)나 사용자 응용 프로그램(외부 스키마)은 영향을 받지 않은 특성
- 예) 데이터 파일 저장 위치 → 다른 디스크로 옮기거나 저장 방식 변경
- DB의 논리적 구조나 사용자는 그 변화를 인지할 필요 없음

## 7. ERD

- 데이터 모델링의 결과를 시각적으로 표현하는 설계도
- DB를 구성하는 데이터 주체(엔터티)와 그들 사이의 관계를 약속된 표기법으로 그린 것
- 사용자, 설계자, 개발자 간의 원활한 의사소통을 돕는 것을 목적

![[01. 데이터 모델의 이해-1791111347488.webp]]

### ERD 작성 순서
- 1. 엔터티를 도출
- 2. 도출된 엔터티를 적절히 배치
- 3. 엔터티 간의 관계를 설정
- 4. 관계명을 기술
- 5. 관계의 참여도를 기술
- 6. 관계의 필수 / 선택 여부를 기술
